ESP MANAGER PROJEKTUEBERGABE
============================
Stand: 0.5.7 / 0.5.7-dev

ZIELBILD
Home-Assistant-Add-on für Arduino-C++-ESP-Projekte mit PlatformIO-Build, USB-Erstinstallation, serieller Diagnose, WLAN-Provisioning, MQTT-Status und später sicherem OTA. Aktuelle Testhardware: ESP32-WROOM-32D und NodeMCU ESP8266MOD.

AKTUELLER FUNKTIONSUMFANG
- Projekt-/Dateiverwaltung, Editor, Backups, Import/Export
- Live-Build, Buildabbruch, Buildhistorie und Mehrchip-Initial-Images
- USB-&-Status-Seite mit ESP Web Tools, serieller Konsole, WLAN-Anleitung und MQTT-Status
- WLAN-Captive-Portal/Fallback und MQTT/OTA-Agent

HARDWAREBEFUND VOR 0.5.7
Der serielle Monitor zeigte eine bereits vorhandene ESP32-AT-Firmware mit Bootloader von 2019, SoftAP/STA und einer alten OTA-Partitionierung. Damit war bewiesen, dass USB/Web Serial funktioniert, aber die ESP-Manager-Firmware noch nicht geschrieben worden war. ESP Web Tools zeigte `Install undefined` und blieb bei `Preparing installation`.

URSACHE UND LOESUNG 0.5.7
Die Hardwareseite war unter `/usb/<projekt>` ohne abschließenden Schrägstrich erreichbar. Der relative Pfad `manifest.json` wurde dadurch als `/usb/manifest.json` statt `/usb/<projekt>/manifest.json` aufgelöst. Die Projektlinks und Route enden jetzt mit `/`. Zusätzlich lädt die Seite das Manifest vorab und zeigt `Bereit: <Name> <Version> / <Chipfamilie>` oder einen konkreten Manifestfehler.

TESTABLAUF
1. Dev-Version 0.5.7 installieren.
2. Projekt neu kompilieren; SUCCESS abwarten.
3. `USB & Status` öffnen.
4. Vor dem Installer muss `Bereit: ... / ESP32` bzw. die passende Familie erscheinen.
5. Erst dann Install starten und den USB-Port auswählen.
6. Nach erfolgreichem Flash seriellen Monitor neu verbinden oder Reset drücken.
7. Erwartet wird `[ESPManager] Agent startet`, nicht mehr der alte ESP-IDF-AT-Bootlog als laufende Anwendung.
8. Danach Fallback-WLAN `ESPManager-<projekt>` und MQTT-Status testen.

WICHTIG
Der Boot-ROM-Starttext eines ESP32 kann weiterhin erscheinen. Entscheidend ist, welche Anwendung danach startet. Vor dem erfolgreichen Flash liefen AT-Firmware und SoftAP; nach dem Flash muss der ESPManager-Agent loggen.

ENTWICKLUNGSREGELN
- Keine Funktionen ungefragt entfernen.
- CHANGELOG.md in Wurzel und beiden Add-on-Ordnern.
- PROJECT_HANDOVER.txt bei jeder Version aktualisieren.
- Stable/Dev trennen, Python prüfen und ZIP testen.

ZIELBILD
Home-Assistant-Add-on zur zentralen Verwaltung von Arduino-C++-ESP-Projekten. Der Benutzer bearbeitet seine Programmlogik, während der ESPManager-Agent WLAN-Provisioning, Router-Fallback, MQTT-Status, Logs und OTA-Grundlagen bereitstellt. Verfügbare Testhardware: ESP32-WROOM-32D und NodeMCU ESP8266MOD. Späteres reales Anwendungsziel: Sagemcom/Netz-Niederoesterreich-M-Bus-Zähler.

ERREICHTER HARDWARE-MEILENSTEIN
- Sichere HA/Tailscale-Seite und Web Serial funktionierten.

URSACHE DES MQTT-FEHLERS
`core-mosquitto` ist der interne Add-on-/Containername, den der ESP im normalen Heimnetz nicht per DNS auflösen kann. Der Add-on-Prozess darf diesen internen Namen weiterverwenden; Firmware benötigt hingegen einen im LAN erreichbaren Hostnamen oder die LAN-IP von Home Assistant.

LOESUNG 0.6.0
Getrennte Konfiguration:
- mqtt_host / mqtt_port / mqtt_username / mqtt_password: Add-on-intern, typischerweise core-mosquitto.
- device_mqtt_host / device_mqtt_port / device_mqtt_username / device_mqtt_password: in Firmware eingebettet und vom ESP im Heimnetz erreichbar.
Standard für device_mqtt_host ist homeassistant.local. Falls mDNS im WLAN nicht funktioniert, muss die LAN-IP des Home-Assistant-Hosts eingetragen werden. Nach Änderung ist ein neuer Firmware-Build erforderlich.

WICHTIG ZU MQTT-ZUGANGSDATEN
Für ESP-Geräte sollte im Mosquitto-Add-on ein zusätzlicher Login verwendet und in den device_mqtt-Feldern eingetragen werden. Leere Zugangsdaten funktionieren nur, wenn der Broker anonyme Verbindungen erlaubt.

ESP MANAGER PROJEKTUEBERGABE - ERGAENZUNG 0.6.3
================================================

Basis: vollständiges Repository 0.6.2. Dieser Patch wird beim Container-Build auf dessen saubere main.py und Agent-Templates angewendet.

HARDWARESTATUS
- ESP32-Browserflash funktioniert.
- Serieller Monitor funktioniert.
- WLAN-Captive-Portal funktioniert.
- MQTT-Broker ist erreichbar, antwortet aber mit PubSubClient-Status 5.

MQTT STATUS 5
Status 5 bedeutet, dass der Broker die Verbindung nicht autorisiert hat. Der Host/DNS-Fehler ist damit überwunden. Zu prüfen sind jetzt ausschließlich die für die Firmware eingebetteten Werte:
- device_mqtt_username
- device_mqtt_password
Diese müssen zu einem im Mosquitto-Add-on erlaubten Geräte-Login passen. Danach Add-on neu starten, Projekt neu kompilieren und Firmware neu flashen, weil die Werte als Build-Flags eingebettet werden.

SERIELLE TRENNUNG
Die bisherige Hardwareseite verwendete TextDecoderStream und pipeTo. Dadurch blieb der zugrunde liegende Port trotz gestoppter Ausgabe gesperrt. 0.6.3 liest Bytes direkt aus port.readable, dekodiert sie mit TextDecoder und verwaltet den Reader explizit. Beim Trennen:
1. keepReading wird false.
2. reader.cancel() beendet den wartenden read()-Aufruf.
3. Der Leseloop führt reader.releaseLock() in finally aus.
4. Erst danach erfolgt port.close().
5. Zustände werden auf null gesetzt und Verbinden wieder freigegeben.

ENTWICKLUNGSREGELN
- Keine vorhandenen Funktionen entfernen.
- Haupt- und Hardwareseiten-JavaScript gerendert testen.
- CHANGELOG.md in Wurzel und beiden Add-on-Ordnern.
- PROJECT_HANDOVER.txt bei jeder Version aktualisieren.
ESP MANAGER PROJEKTUEBERGABE - ERGAENZUNG 0.6.4
================================================

BASIS
Vollständiges Repository 0.6.2 plus Patch 0.6.3. 0.6.4 wird als Overlay eingespielt und beim Container-Build nach patch_v063.py angewendet.

BESTÄTIGTER HARDWARESTATUS
- ESP32-Browserflash funktioniert.
- Serieller Monitor funktioniert.
- WLAN-Captive-Portal funktioniert.
- ESP meldet seriell `MQTT verbunden`.
- Damit sind WLAN, Broker-Erreichbarkeit und Geräte-Anmeldedaten praktisch bestätigt.

PROBLEM DES MQTT-STATUSMONITORS
Die Hardwareseite rief den Gerätestatus über einen relativen Pfad wie `../../api/devices/<projekt>` ab. Unter Home-Assistant-Ingress konnte dieser Pfad aus dem Add-on-Präfix herauslaufen und die Home-Assistant-API statt der ESP-Manager-API treffen. Das erklärt `503 Service Unavailable`. Zusätzlich war die Geräte-ID fest an den Projektnamen gebunden, ohne Auswahlmöglichkeit.

LÖSUNG 0.6.4
- Die Hardwareseite ermittelt den Add-on-Basispfad aus dem Teil vor `/usb/` in `location.pathname`.
- Alle Status-API-Aufrufe verwenden diesen Basispfad.
- `/api/mqtt/status` zeigt, ob das Add-on selbst mit MQTT verbunden ist und wie viele Geräte erkannt wurden.
- `/api/devices` füllt eine Auswahlliste.
- Das Gerät mit derselben ID wie das Projekt wird bevorzugt.
- Falls genau ein Gerät erkannt wurde, wird es automatisch gewählt.
- Andernfalls kann der Benutzer ein Gerät auswählen.

WICHTIGE MQTT-ZUORDNUNG
Die Firmware veröffentlicht auf `espmanager/<device_id>/...`. device_id entspricht aktuell dem Projektnamen beim Build. Bei duplizierten oder umbenannten Projekten muss der zuletzt geflashte Gerätename in der Auswahl verwendet werden.

NÄCHSTER SCHRITT

1. OTA-Endpunkt und Schaltfläche wieder sauber integrieren.
2. OTA-Fortschritt und Fehlerstatus anzeigen.
3. SHA256-Prüfung und sichere Firmwarefreigabe ergänzen.
4. Geräte dauerhaft einem Projekt zuordnen.

ZIEL DER AUSBAUSTUFE

PROJEKT-GERÄTE-ZUORDNUNG
- espmanager.yaml erhält optional `device_id`.
- Auswahl eines Geräts auf der Hardwareseite speichert die Zuordnung.
- Beim erneuten Öffnen wird das zugeordnete Gerät bevorzugt.
- Ist nur ein Gerät erkannt, bleibt die automatische Auswahl erhalten.

OTA-WORKFLOW
1. Benutzer wählt ein online erkanntes Gerät.
2. Benutzer wählt einen erfolgreichen Build aus der Historie.
3. Backend liest firmware.bin und vergleicht den aktuellen SHA256-Wert mit manifest.json.
4. Backend erzeugt eine token-geschützte Download-URL aus public_base_url.
5. MQTT-Kommando geht mit QoS 1 an `espmanager/<device>/cmd/ota` und enthält URL, Version, Build-ID, Dateigröße und SHA256.
6. Agent prüft den OTA-Token.
7. HTTPUpdate meldet Start, Fortschritt, Ende und Fehler über Callbacks.
8. Agent publiziert JSON auf `espmanager/<device>/ota/progress` und gibt dasselbe seriell aus.
9. Hardwareseite aktualisiert Fortschrittsbalken, Status und OTA-Protokoll.
10. Nach erfolgreichem Update führt HTTPUpdate den vorgesehenen Neustart aus.

INTEGRITÄT UND SICHERHEIT
- SHA256 wird serverseitig direkt vor OTA-Auftrag und Firmwareauslieferung erneut gegen das Buildmanifest geprüft.
- Firmwaredownload benötigt den projektspezifischen OTA-Token.
- Zusätzlich liefert der Server `x-MD5`, den die HTTPUpdate-Implementierung für ihre Downloadprüfung verwenden kann.
- Die über MQTT mitgesendete SHA256 wird am Gerät protokolliert. Eine eigenständige geräteseitige SHA256-Neuberechnung ist in 0.7.0 noch nicht implementiert und bleibt eine Härtungsaufgabe.
- public_base_url muss aus dem WLAN des ESP erreichbar sein. Für Dev typischerweise `http://<HA-LAN-IP>:8100`, für Stable Port 8099.

ZURÜCK-NAVIGATION
Die Hardwareseite berechnet den Add-on-Basispfad aus dem tatsächlichen Ingress-Pfad vor `/usb/`. Der Zurück-Button navigiert direkt zu diesem Basispfad, nicht mehr über `../..`.

5. Systembibliotheken des Agenten dürfen nicht vom Expertenfeld abhängen. WiFiManager, PubSubClient und ArduinoJson werden automatisch in lib_deps eingefügt.

ESP MANAGER HOME ASSISTANT ADD-ON - PROJEKTUEBERGABE
=====================================================

Stand: Version 0.3.0 stable / 0.3.0-dev development
Ziel: ESPHome-aehnliche zentrale Verwaltung fuer ESP-Boards, aber mit Arduino C++ statt YAML-Logik. Spaeter optional MicroPython.

1. ZIELBILD
-----------
Der Benutzer moechte ESP-Boards zentral in Home Assistant verwalten. Die eigentliche Programmlogik soll in Arduino C++ geschrieben werden. OTA, MQTT-Status, Logs, WLAN-Provisioning und Home-Assistant-nahe Verwaltung sollen nicht jedes Mal manuell in den Projektcode eingebaut werden muessen.

Gewuenschtes Bedienmodell:
- Home Assistant Add-on oeffnen
- Projekt anlegen
- Board waehlen
- Code in der Weboberflaeche bearbeiten
- in Home Assistant kompilieren
- initial per Browser/Web Serial flashen
- danach per OTA aktualisieren
- Geraetestatus, Logs und Firmware zentral sehen

Das erste echte Zielgeraet ist ein ESP mit Sagemcom/Netz-Niederoesterreich-Zaehlerauslesung ueber M-Bus-Wandler. Der funktionierende Arduino-Decoder soll erhalten bleiben und nur in das neue Wrapper-Konzept eingebettet werden.

2. ARCHITEKTUR
--------------
Repository-Layout:

ha_esp_manager_addons_repo/
  repository.json
  README.md
  UPDATE_WORKFLOW.md
  CHANGELOG.md
  PROJECT_HANDOVER.txt
  esp_manager/
  esp_manager_dev/

Add-ons:
- esp_manager: stabilerer Teststand
- esp_manager_dev: Entwicklungskanal

Home-Assistant-Add-on:
- FastAPI Webserver
- PlatformIO Build-System im Container
- Debian/Python-slim Base Image, weil Alpine Probleme mit der ESP32-Toolchain verursachte
- Web UI mit Projektliste, Geraeteliste, Editor und Live-Build-Log
- MQTT-Anbindung an Mosquitto
- Browser-Flash-Seite mit ESP Web Tools

Datenablage in Home Assistant:
- Projekte: /config/esp_manager/projects/<projektname>/
- Firmware: /config/esp_manager/firmware/<projektname>/firmware.bin
- Manifest: /config/esp_manager/firmware/<projektname>/manifest.json

3. WRAPPER-KONZEPT
------------------
Neue Projekte arbeiten im Wrapper-Modus.

Benutzer-Code:

void setupDevice() {
  // eigenes Setup
}

void loopDevice() {
  // eigene Logik
}

Vom Add-on erzeugter Rahmen:

void setup() {
  ESPManager.begin();
  setupDevice();
}

void loop() {
  ESPManager.loop();
  loopDevice();
}

Dadurch bleibt OTA/MQTT/WLAN/Status immer im Agent und Benutzer-Code bleibt auf die eigentliche Anwendung fokussiert.

4. ESPMANAGER AGENT
-------------------
Der Agent liegt im Template:

esp_manager/app/templates/lib/ESPManager/src/

Funktionen:
- WLAN-Provisioning mit WiFiManager Captive Portal
- MQTT-Verbindung
- Statusmeldungen an espmanager/<device_id>/status
- Availability an espmanager/<device_id>/availability
- Logausgabe an espmanager/<device_id>/log
- Restart-Kommando ueber MQTT
- OTA-Kommando ueber MQTT
- einfacher Sensor-Publish als Beispiel

Wichtig: OTA-Kommandos werden nur akzeptiert, wenn der im MQTT-Payload gesendete Token mit ESPMANAGER_OTA_TOKEN uebereinstimmt.

5. MQTT TOPICS
--------------
Geraet -> Add-on:
- espmanager/<device_id>/status
- espmanager/<device_id>/availability
- espmanager/<device_id>/log
- espmanager/<device_id>/ota/progress

Add-on -> Geraet:
- espmanager/<device_id>/cmd/restart
- espmanager/<device_id>/cmd/ota

OTA-Payload enthaelt:
- token
- url
- sha256
- size
- version

6. BEREITS GELOESTE PROBLEME
----------------------------
Problem: Lokales Add-on musste deinstalliert und neu installiert werden.
Loesung: Repository-Layout mit esp_manager und esp_manager_dev erstellt. Zukuenftig Version in config.yaml erhoehen und ueber Add-on Store aktualisieren.

Ursache: Alpine-basierter Container war fuer PlatformIO/ESP32-Toolchain ungeeignet.
