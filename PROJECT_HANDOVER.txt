ESP MANAGER HOME ASSISTANT ADD-ON - PROJEKTUEBERGABE
=====================================================

Stand: Version 0.3.0 stable / 0.3.0-dev development
Ziel: ESPHome-aehnliche zentrale Verwaltung fuer ESP-Boards, aber mit Arduino C++ statt YAML-Logik. Spaeter optional MicroPython.

1. ZIELBILD
-----------
Der Benutzer moechte ESP-Boards zentral in Home Assistant verwalten. Die eigentliche Programmlogik soll in Arduino C++ geschrieben werden. OTA, MQTT-Status, Logs, WLAN-Provisioning und Home-Assistant-nahe Verwaltung sollen nicht jedes Mal manuell in den Projektcode eingebaut werden muessen.

Gewuenschtes Bedienmodell:
- Home Assistant Add-on oeffnen
- Projekt anlegen
- Board waehlen
- Code in der Weboberflaeche bearbeiten
- in Home Assistant kompilieren
- initial per Browser/Web Serial flashen
- danach per OTA aktualisieren
- Geraetestatus, Logs und Firmware zentral sehen

Das erste echte Zielgeraet ist ein ESP mit Sagemcom/Netz-Niederoesterreich-Zaehlerauslesung ueber M-Bus-Wandler. Der funktionierende Arduino-Decoder soll erhalten bleiben und nur in das neue Wrapper-Konzept eingebettet werden.

2. ARCHITEKTUR
--------------
Repository-Layout:

ha_esp_manager_addons_repo/
  repository.json
  README.md
  UPDATE_WORKFLOW.md
  CHANGELOG.md
  PROJECT_HANDOVER.txt
  esp_manager/
  esp_manager_dev/

Add-ons:
- esp_manager: stabilerer Teststand
- esp_manager_dev: Entwicklungskanal

Home-Assistant-Add-on:
- FastAPI Webserver
- PlatformIO Build-System im Container
- Debian/Python-slim Base Image, weil Alpine Probleme mit der ESP32-Toolchain verursachte
- Web UI mit Projektliste, Geraeteliste, Editor und Live-Build-Log
- MQTT-Anbindung an Mosquitto
- Browser-Flash-Seite mit ESP Web Tools

Datenablage in Home Assistant:
- Projekte: /config/esp_manager/projects/<projektname>/
- Firmware: /config/esp_manager/firmware/<projektname>/firmware.bin
- Manifest: /config/esp_manager/firmware/<projektname>/manifest.json

3. WRAPPER-KONZEPT
------------------
Neue Projekte arbeiten im Wrapper-Modus.

Benutzer-Code:

void setupDevice() {
  // eigenes Setup
}

void loopDevice() {
  // eigene Logik
}

Vom Add-on erzeugter Rahmen:

void setup() {
  ESPManager.begin();
  setupDevice();
}

void loop() {
  ESPManager.loop();
  loopDevice();
}

Dadurch bleibt OTA/MQTT/WLAN/Status immer im Agent und Benutzer-Code bleibt auf die eigentliche Anwendung fokussiert.

4. ESPMANAGER AGENT
-------------------
Der Agent liegt im Template:

esp_manager/app/templates/lib/ESPManager/src/

Funktionen:
- WLAN-Provisioning mit WiFiManager Captive Portal
- MQTT-Verbindung
- Statusmeldungen an espmanager/<device_id>/status
- Availability an espmanager/<device_id>/availability
- Logausgabe an espmanager/<device_id>/log
- Restart-Kommando ueber MQTT
- OTA-Kommando ueber MQTT
- einfacher Sensor-Publish als Beispiel

Wichtig: OTA-Kommandos werden nur akzeptiert, wenn der im MQTT-Payload gesendete Token mit ESPMANAGER_OTA_TOKEN uebereinstimmt.

5. MQTT TOPICS
--------------
Geraet -> Add-on:
- espmanager/<device_id>/status
- espmanager/<device_id>/availability
- espmanager/<device_id>/log
- espmanager/<device_id>/ota/progress

Add-on -> Geraet:
- espmanager/<device_id>/cmd/restart
- espmanager/<device_id>/cmd/ota

OTA-Payload enthaelt:
- token
- url
- sha256
- size
- version

6. BEREITS GELOESTE PROBLEME
----------------------------
Problem: Lokales Add-on musste deinstalliert und neu installiert werden.
Loesung: Repository-Layout mit esp_manager und esp_manager_dev erstellt. Zukuenftig Version in config.yaml erhoehen und ueber Add-on Store aktualisieren.

Problem: Button "Anlegen" funktionierte in Home Assistant Ingress nicht.
Ursache: absolute API-Pfade und unsaubere globale DOM-Variablen.
Loesung: relative Pfade wie api/projects und explizite Element-Zugriffe.

Problem: Build blieb scheinbar bei "Build laeuft" stehen.
Ursache: Build war synchron, Log erschien erst am Ende.
Loesung in 0.3.0: Build-Jobs laufen im Hintergrundthread, die UI pollt /api/builds/<job_id> und zeigt Live-Logs.

Problem: ESP32-Build schlug fehl mit xtensa-esp32-elf-g++: not found.
Ursache: Alpine-basierter Container war fuer PlatformIO/ESP32-Toolchain ungeeignet.
Loesung: Wechsel auf docker.io/library/python:3.12-slim-bookworm und apt-Pakete.

Problem: Benutzer moechte Code direkt bearbeiten.
Loesung in 0.3.0: einfacher Webeditor fuer src/device.cpp und src/main.cpp mit Laden/Speichern.

8. BEKANNTE EINSCHRAENKUNGEN
----------------------------
- SHA256 wird serverseitig berechnet, aber der ESP prueft die Firmware noch nicht selbst gegen SHA256.
- OTA-Rollback/Partitionslayout fuer ESP32 ist noch nicht sauber konfiguriert.
- Webeditor ist minimal, kein Monaco/VS-Code-Editor.
- Kein Datei-Browser, nur feste Dateien im Dropdown.
- Kein Projektimport-Assistent fuer bestehende Arduino-Projekte.
- Kein Legacy-Modus fuer bestehenden setup()/loop()-Code.
- Keine MicroPython-Unterstuetzung.
- Keine echte Benutzer/Rechte-Logik ausser Home-Assistant/Add-on-Zugriff.
- ESP Web Tools erfordert geeigneten Browser und HTTPS/vertrauenswuerdigen Kontext je nach Umgebung.
- public_base_url muss zur HA-Installation passen, z. B. http://homeassistant.local:8099 oder IP-Adresse.

10. UPDATE-WORKFLOW
-------------------
Bei jeder Aenderung:
1. Code aendern.
2. Version in esp_manager_dev/config.yaml erhoehen.
3. Repository pushen.
4. In Home Assistant Add-on Store "Nach Updates suchen".
5. ESP Manager Dev aktualisieren.
6. Testen.
7. Wenn stabil, Aenderungen nach esp_manager uebernehmen und dort Version erhoehen.

12. WICHTIGE ENTWICKLUNGSREGELN
-------------------------------

14. HINWEIS FUER NEUEN COPILOT CHAT
------------------------------------
Wenn dieser Code und diese Datei in einen neuen Chat geladen werden, soll die Weiterentwicklung auf Version 0.3.0 aufbauen. Nicht auf fruehere ZIP-Versionen zurueckfallen. Hauptziel bleibt: zentrale Home-Assistant-Verwaltung fuer Arduino-C++-basierte ESPs, mit moeglichst wenig Verwaltungslogik im Benutzer-Code.

15. STABLE/DEV ISOLATION IN 0.3.0
----------------------------------
Stable nutzt:
- Port/Ingress: 8099
- Daten: /config/esp_manager

Dev nutzt:
- Port/Ingress: 8100
- Daten: /config/esp_manager_dev

Damit koennen Stable und Dev besser parallel getestet werden, ohne Projektdateien und HTTP-Port direkt zu kollidieren.
